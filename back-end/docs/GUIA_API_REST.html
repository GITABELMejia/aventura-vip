1. Introducción

Este documento es la guía de uso de la API REST del sistema de movilidad de la empresa Aventura Vip de Cusco, la cual brinda servicio de taxis corporativo al grupo Belmond (hoteles Monastery y Nazarenas).

Esta primera versión implementa el módulo de Autenticación (Login): la parte del sistema que valida las credenciales de un usuario y emite un token JWT que identifica a la persona en todas las peticiones futuras.

El backend está desarrollado en Node.js con Express y TypeScript, y usa PostgreSQL 15 como base de datos. La lógica de negocio vive en procedimientos almacenados de PostgreSQL, por lo que la API es una "capa fina" que conecta las peticiones HTTP con la base de datos.

2. Arquitectura del sistema

El flujo completo del login funciona de la siguiente manera:

  Cliente (curl / futura app)
      |
      | 1. POST /api/auth/login  {correo_o_dni, clave}
      v
  Servidor Node.js (Express) --- src/modules/auth/auth.controller.ts
      |  (morgan registra cada peticion HTTP en la consola)
      |
      | 2. Llama al procedimiento  SELECT SP_LOGIN($1, $2)
      v
  PostgreSQL 15 --- valida credenciales, devuelve datos + permisos (JSONB)
      |
      | 3. Respuesta JSON
      v
  Servidor: firma el token JWT (12 horas de vigencia)
      |
      | 4. Respuesta HTTP 200  {token, usuario}
      v
  Cliente: guarda el token y lo envia en el encabezado Authorization
      |
      | 5. GET /api/auth/me  (Authorization: Bearer <token>)
      v
  Middleware autenticarToken valida la firma y expiracion del token
      |
      v
  Se devuelven los datos del usuario autenticado

3. Requisitos previos

Para ejecutar este proyecto se necesita:

  • Node.js versión 18 o superior (incluye npm).
  • Docker (para correr PostgreSQL 15 sin instalarlo en el sistema).
  • Python 3 (opcional, solo para regenerar este PDF).
  • curl o Postman para probar los endpoints.

4. Instalación y puesta en marcha

4.1. Base de datos (PostgreSQL 15 en Docker)

Levantar el contenedor con PostgreSQL 15:

docker run --name av-test-pg -e POSTGRES_USER=aventura \
  -e POSTGRES_PASSWORD=aventura123 -e POSTGRES_DB=aventura_vip \
  -p 5432:5432 -d postgres:15-alpine

Crear e inyectar los scripts SQL (en este orden obligatorio):

cd "back-end"
npm run db:init

O ejecutar manualmente cada script en orden:

docker exec -i av-test-pg psql -U aventura -d aventura_vip < db/00_SCHEMA.SQL
docker exec -i av-test-pg psql -U aventura -d aventura_vip < db/02_AUDIT_TRIGGER.SQL
docker exec -i av-test-pg psql -U aventura -d aventura_vip < db/01_PROCEDURES.SQL
docker exec -i av-test-pg psql -U aventura -d aventura_vip < db/03_SEEDS.SQL

El orden importa porque cada script usa lo que crea el anterior:

  • 00_SCHEMA.SQL - crea las tablas.
  • 02_AUDIT_TRIGGER.SQL - crea los triggers de auditoría.
  • 01_PROCEDURES.SQL - crea los procedimientos almacenados.
  • 03_SEEDS.SQL - inserta roles, empresas y cuentas de prueba.

4.2. Servidor API

Instalar las dependencias y compilar el TypeScript:

cd "back-end"
npm install
npm run build

Levantar el servidor (dos opciones):

npm start        # ejecuta la versión compilada (recomendado en producción)
npm run dev      # modo desarrollo (se recarga al guardar)

El servidor escucha en http://localhost:3000.

Configuración (archivo .env):

PORT=3000
DATABASE_URL=postgres://aventura:aventura123@localhost:5432/aventura_vip
JWT_SECRET=aventura_vip_super_secreto_2026_cambiar_en_produccion
JWT_EXPIRES_IN=12h

5.1. Registro de peticiones con Morgan

El backend utiliza morgan, un middleware de Express que registra en la consola cada petición HTTP que recibe la API. Esto facilita el monitoreo, la depuración y el diagnóstico de errores en tiempo real.

Al ejecutar el servidor, cada petición genera una línea de log con el método HTTP, la ruta, el código de estado y el tiempo de respuesta: 

GET / 200 3.247 ms - 154
POST /api/auth/login 200 101.699 ms - 751
POST /api/auth/login 401 24.025 ms - 36

El color de la salida también es útil: verde indica éxito (2xx) y amarillo indica advertencias (4xx, como un login rechazado).

7. Autenticación con tokens JWT

El sistema usa JSON Web Tokens (JWT) para la autenticación:

  • Cuando un usuario inicia sesión con credenciales válidas, el servidor firma un token con la clave secreta JWT_SECRET.
  • El token dura 12 horas (configurable en JWT_EXPIRES_IN).
  • El token contiene el id del usuario, su rol y sus permisos. Así la API no necesita consultar la base en cada petición.
  • Para acceder a rutas protegidas, el cliente envía el token en el encabezado: Authorization: Bearer <token>.
  • El middleware autenticarToken verifica la firma y la expiración; si algo falla, responde HTTP 401.

Regla de identificador de acceso (validada en SP_LOGIN):

  • Trabajadores de Aventura Vip y de los hoteles (Belmond) - DNI (8 dígitos).
  • App pública (empresa "Particular") - correo electrónico.
  • El login tiene rate limit: 5 intentos por IP por minuto (HTTP 429).

9. Ejemplos de uso con curl

9.1. Iniciar sesión (trabajador, por DNI)

curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"correo_o_dni":"12345678","clave":"demo123"}'

9.2. Iniciar sesión (app pública, por correo)

curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"correo_o_dni":"usuario@app.com","clave":"demo123"}'

9.3. Consultar el perfil (/me) con el token

Paso 1: guardar el token en una variable:

TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"correo_o_dni":"12345678","clave":"demo123"}' \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['token'])")

Paso 2: usarlo en el endpoint protegido:

curl http://localhost:3000/api/auth/me \
  -H "Authorization: Bearer $TOKEN"

9.4. Ejemplo de error: credenciales incorrectas

curl -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"correo_o_dni":"12345678","clave":"clave_equivocada"}'
# Respuesta: {"mensaje":"Credenciales invalidas"}   (HTTP 401)

9.5. Ejemplo de error: sin token

curl http://localhost:3000/api/auth/me
# Respuesta: {"mensaje":"No se envió un token de acceso"}   (HTTP 401)

9.6. Ejemplo de error: rate limit (fuerza bruta)

# Tras 5 intentos fallidos en un minuto, la API responde:
# {"mensaje":"Demasiados intentos de acceso. Espera un momento..."}  (HTTP 429)

9.7. Listar usuarios (requiere permiso GESTIONAR_USUARIOS o CREAR_USUARIOS)

curl "http://localhost:3000/api/usuarios?q=&rol=&estado=" \

11. Buenas prácticas de seguridad

  • Las claves se almacenan cifradas con bcrypt (nunca en texto plano).
  • El servidor nunca devuelve la clave en las respuestas.
  • Los errores de login usan el mismo mensaje genérico ("Credenciales invalidas") para no revelar si el identificador o la clave fue lo incorrecto.
  • helmet añade cabeceras HTTP seguras (CSP, X-Frame-Options, HSTS).
  • CORS restringido a los orígenes configurados en CORS_ORIGENES (en producción se agrega el dominio del sistema).
  • Rate limit en el login (5 intentos por IP por minuto, HTTP 429).
  • Control de acceso por permisos (PBAC): cada endpoint declara el permiso que exige y el middleware responde HTTP 403 si falta.
  • El archivo .env con JWT_SECRET no debe subirse a repositorios públicos; en producción usar un gestor de secretos.
  • Los tokens expiran (12 h); los usuarios inactivos pierden el acceso aunque su token siga "vigente" (validación con SP_VALIDAR_USUARIO).
  • El 100% de las consultas se ejecutan mediante procedimientos almacenados con parámetros (protección contra inyección SQL).
  • En producción se debe servir la API por HTTPS.

12. Aplicación web (frontend) y modo PWA

12.1. Frontend (React + Vite)

El frontend es una SPA (Single Page Application) desarrollada en React con Vite, Tailwind CSS y TypeScript. Usa axios para llamar a la API, react-router-dom para la navegación y vite-plugin-pwa para convertir la app en una PWA (Progressive Web App): instalable y funcional sin conexión.

Instalar las dependencias y arrancar el servidor de desarrollo:

cd "front-end"
npm install
npm run dev

El servidor de desarrollo escucha en http://localhost:5173 y redirige todas las peticiones /api hacia el backend (puerto 3000) mediante server.proxy en vite.config.ts.

Generar el build de producción (incluye manifest y service worker):

npm run build
npm run preview

El build genera dist/sw.js (service worker), el dist/manifest.webmanifest y el registro automático (dist/registerSW.js).

12.2. Probar en el celular (red local)

Opción A: abrir la app con el navegador de un celular en la misma red Wi-Fi.

  1. En vite.config.ts debe estar server.host: true para exponer el servidor hacia la red local (ya configurado).
  2. Conocer la IP local del Mac: ipconfig getifaddr en0.
  3. En el celular abrir http://IP_DEL_MAC:5173.

El login y toda la app funcionan normalmente, pero no se puede instalar: los navegadores exigen HTTPS para habilitar el service worker y la instalación.

12.3. PWA instalable con túnel HTTPS (cloudflared)

Opción B: exponer la app por HTTPS con un túnel gratuito de Cloudflare (cloudflared) para que el navegador permita instalar la app y usarla sin internet.

1) Generar el build de producción y servirlo:

cd "front-end"
npm run build
npm run preview -- --host

2) Descargar el binario de cloudflared (no requiere Homebrew; se obtiene de GitHub Releases y se coloca en ~/.local/bin): en Apple Intel usar cloudflared-darwin-amd64.tgz; en Apple Silicon usar cloudflared-darwin-arm64.tgz. 

curl -L -o cloudflared.tgz https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-darwin-amd64.tgz
tar -xzf cloudflared.tgz
chmod +x cloudflared
mv cloudflared ~/.local/bin/

3) Abrir el túnel hacia el preview (puerto 4173):

~/.local/bin/cloudflared tunnel --url http://localhost:4173

4) Del log del túnel tomar la URL pública https://XXXX.trycloudflare.com y abrirla en el celular. Ahí ya aparece la instalación: en Android/Chrome desde el menú "Instalar aplicación"; en iPhone/Safari en "Compartir" y luego "Añadir a pantalla de inicio".

Si el preview responde HTTP 403 para el host del túnel, es porque Vite bloquea nombres de host desconocidos; se resuelve con preview.allowedHosts: true en vite.config.ts.

La URL del túnel es temporal (cambia al reiniciar el túnel) y, mientras esté activa, la app queda expuesta a Internet; conviene cerrar el túnel al terminar de probar (pkill cloudflared).
